## 0. 검토 전제

이번 검토는 세 가지 결론을 전부 열어둔 상태로 진행했다 — "출시 가능하다", "개인 사용만 유지하는 게 낫다", **"경험과 이번 조사 자료만 남기고 백지에서 다시 시작한다"** 모두 유효한 결론이다. 재검토 범위는 세 축으로 나눴고, **콘텐츠(①)·학습 설계(②)가 최우선, 기술 스택(③)은 그다음 우선순위**로 판단했다(사용자 확정 사항).

| 축 | 의미 | 우선순위 |
|---|---|---|
| ① 콘텐츠 | 문장 3,622개·단어 3,920개·콜로케이션 5,705개 — 데이터 자체의 품질·저작권·활용 가능성 | 최우선 |
| ② 학습 설계 | FSRS+문장중심+쉐도잉+대화라는 학습 방법론 자체가 유효한 방향인지 | 최우선 |
| ③ 기술 스택 | Next.js/Neon/Drizzle 웹 스택, 그리고 네이티브 앱을 만든다면 무엇으로 만들지 | 차순위 |

## 1. 결론부터

**개인 사용은 이미 성립하고 있다.** 지금 상태로도 매일 쓸 수 있는 완성도(FSRS, 게이미피케이션, 쉐도잉, 테스트 69+102블록)를 갖췄다 — 이 축은 "활용 어려움" 판정이 나오지 않는다.

**웹 공개 배포(PWA)는 현실적으로 가능하다.** 비용은 월 $0~40 수준(§5), 기술 스택을 바꿀 이유도 발견되지 않았다. 다만 인증·보안(IDOR)·배포 인프라가 전무해 1~3주 분량의 선행 작업이 필요하다.

**스토어 등록은 플랫폼별로 난이도가 갈린다.** Android(Google Play, PWA→TWA)는 도구·정책·성공 사례가 모두 확인돼 현실적이다. iOS는 앱스토어 경로 자체가 구조적으로 불리하다(§4) — 대신 iOS는 이미 만들어둔 PWA의 "홈 화면에 추가"가 스토어 없이도 정상 동작하고 iOS 26부터 오히려 더 좋아졌다.

**수익은 낙관하기 어렵다.** 광고는 한국 eCPM 기준 1,000 DAU라도 월 90만 원 안팎이고, 구독은 업계 중앙값 자체가 낮다(출시 1년 후 중앙값 월 $72, RevenueCat 2026판) — 이건 SenTalk만의 문제가 아니라 인디 앱 전반의 통계다. **"의미 있는 수익"을 목표로 잡으면 이 축은 활용이 어렵다고 볼 근거가 충분하다.** "서버비 충당" 정도가 현실적 눈높이다.

**콘텐츠는 대부분 안전하지만 국지적 위험이 있다.** AI 생성 콜로케이션·예문, 공개도메인 성격의 우화·속담은 문제없다. `quote`(명언)·`movie`(영화 대사) day_type 문장은 저작권 검토가 전무하고, 광고 수익 모델을 택하는 순간 인용·공정이용 법리가 불리해진다(§2.1). **이 슬라이스는 "백지 재시작"이 아니라 국소 치환으로 충분히 해결 가능한 규모**라고 판단한다.

**학습 설계는 방향이 이미 맞게 가고 있다.** 시장 조사(§2.2)가 보여준 "AI에 잠식되는 건 순수 드릴, 살아남는 건 발화+동기 설계"라는 패턴과 SenTalk의 재설계 방향(19번 SSOT: 쉐도잉·대화 강화)이 우연히 일치한다.

**기술 스택 중 재검토가 실제로 필요한 지점은 하나다**: ADR-001이 "Flutter 완전 재작성이 최적"이라고 결론 내렸는데, 이번 조사로 나온 반대 근거(§4.5 — React/TS 숙련자에게는 RN/Expo가 언어·로직을 상당 부분 보존한다)가 그 결론과 정면으로 충돌한다. 이건 **ADR-001을 다시 열어야 한다는 뜻**이지, 지금 쓰는 Next.js 웹 스택을 버려야 한다는 뜻은 아니다.

**종합**: "백지 재시작"을 지지하는 근거는 콘텐츠 축의 일부(quote·movie 슬라이스)와 기술스택 축의 일부(ADR-001의 Flutter 결론)에 국한된다. 학습 설계와 웹 스택 전체를 버릴 근거는 이번 조사에서 나오지 않았다. 다만 이건 조사자의 판단일 뿐이고, 최종 결정은 사용자 몫이다 — §7에서 결정 단위별로 나눠뒀다.

## 2. 축별 판단 (① 콘텐츠, ② 학습 설계 — 최우선)

### 2.1 콘텐츠(영어 학습 데이터)

**데이터 구성** (문장 3,622개, 대화 539줄 포함 · 단어 3,920개 · 콜로케이션 5,705개):

| 출처 유형 | 생성 방식 | 저작권 리스크 |
|---|---|---|
| 콜로케이션 5,705개 | AI 생성 (`source='ai_generated'` 기본값) | 낮음 |
| 단어 예문(A1~B2) | AI 생성 (프롬프트 배치 → 결과 JSON) | 낮음 |
| 커리큘럼 문장 — `real`/`review` | 수작업 편성(Excel) | 낮음 |
| 커리큘럼 문장 — `tale`(우화)·`proverb`(속담) | 대부분 공개도메인 성격(이솝우화 등) | 낮음 |
| 커리큘럼 문장 — **`quote`(명언)·`movie`(영화 대사)** | 실제 명언·영화 대사 verbatim 수록 | **검토 전무 — 최대 리스크** |
| 외부 코퍼스(NGSL·WordNet·OEW·CEFR-J) | — | ADR-007로 광고 수익 전제 정리 완료 |

`sources` 테이블(667행)에 출처(title/author/year/url)는 기록돼 있으나 **라이선스 판단 자체는 어디에도 없다.** **4개년 전체 실측(2026-07-27): `quote` 222개 + `movie` 119개 = 341개(전체 3,622의 9.4%)** — 사전 추정(year1 각 48개)보다 훨씬 크다. 무료·개인용이면 인용 법리로 방어 여지가 있지만 **광고 수익 모델을 택하는 순간 저작권법 제28조(인용, 주종관계 요건)와 제35조의5(공정이용, 영리성이 불리 요소)가 모두 불리해진다**(법률 자문 아님, §4 참고). **추가 검토 대상**: `news`(120)·`ted`(64)·`drama`(30)·`interview`(23)·`comedy`(14) 등도 실제 저작물 verbatim이면 저작권 리스크 계열 — 즉 위험 범위가 quote·movie만이 아니다. **처리 방침은 [ADR-010](../adr/010_content-copyright-and-data-model.md)에서 확정**: 공개분은 저작권 free(자작·AI생성·AI재작성·PD)만, 원문은 `content_originals` 테이블로 격리(공개 API·git·CSV·백업 제외, admin 전용), 위험 슬라이스는 AI 재작성이 기본. 광고(영리) 모델이라 인용·공정이용 항변이 불리하고 출처표시는 면책 수단이 아니라는 점이 근거.

**판단**: 콘텐츠 전체를 버릴 근거는 없다 — 대부분은 AI 생성이거나 공개도메인 성격이라 안전하다. 위험은 `quote`·`movie` 슬라이스에 국한된 국지적 문제이고, 이는 "AI로 재생성" 또는 "PD·라이선스 소스로 교체"라는 **경계가 분명한 작업**이다. 백지 재시작을 택하더라도 이 슬라이스만 다시 만들면 되지, 3,622개 문장 전체를 버릴 이유는 데이터가 뒷받침하지 않는다. 단, 정확한 전체 개수 집계와 About 페이지 출처 표기(코퍼스 라이선스 문서의 미완 항목 CHK-7), 광고 SDK 도입 전 변호사 검토(CHK-8)는 출시 여부와 무관하게 처리해야 한다.

### 2.2 학습 설계

**현재 설계**: FSRS 간격반복 + 하루 1~2문장 + 쉐도잉(Tier 0, 완료) + 매일 대화(C1, 완료) + 녹음-자가비교(P1, 예정) + 서버 STT(P2, 게이트 뒤 선택).

**시장이 보여준 패턴** (§5 리서치): AI 시대에 "순수 자동화(단순 플래시카드 드릴)"는 무료 LLM(ChatGPT Advanced Voice, Duolingo Max)에 가장 크게 잠식되는 반면, **발화 연습 + 동기 설계가 결합된 서비스는 견조하다** — Speak(AI 스피킹, ARR $100M)의 성공이 정확히 이 축이다. 듀오링고 주가가 GPT-5 데모 후 급락한 것도 "순수 드릴은 AI가 대체 가능"이라는 시장의 재평가였다(사업 자체는 그 시점에도 +39% 성장 중이었다 — 주가와 사업 펀더멘털은 별개).

**판단**: SenTalk의 재설계 방향(19번 SSOT — 쉐도잉·매일 대화 강화)은 이 패턴과 우연히 일치한다. "하루 1문장+FSRS"만 있었다면 순수 드릴 카테고리에 가까웠겠지만, 발화 축(쉐도잉→녹음→선택적 STT)을 이미 사다리로 설계해뒀다는 점에서 방향성을 뒤집을 근거는 찾지 못했다. 다만 이건 "시장에서 통하는 방향과 일치한다"는 것이지 "완성도가 충분하다"는 뜻은 아니다 — 대화 커버리지가 41/48개월이고 페이스(1문장/일)가 "일상 소통"이라는 목표에 충분한지는 **이 리서치가 답할 수 없는 질문**이다(도그푸딩으로 검증할 사안).

## 3. 축별 판단 (③ 기술 스택 — 차순위)

### 3.1 웹 계층 — 유지가 근거 있는 결론

Next.js 16 + Neon PostgreSQL + Drizzle 스택을 바꿀 이유는 조사에서 나오지 않았다. 코드 품질(Unit 69 + E2E ~102블록×2)과 비용 구조(§5) 모두 양호하다. PWA 자산(manifest, service worker, 아이콘)도 이미 완비돼 있다.

### 3.2 네이티브 앱 계층 — ADR-001 재검토 필요

ADR-001(2026-04-12 작성)은 "WebView 래퍼는 비권장, Flutter 완전 재작성이 최적(1인 2~3개월)"이라고 결론 냈다. 이번 조사는 그 이후 나온 정보로 이 결론에 세 가지 이의를 제기한다.

| ADR-001의 전제 | 이번 조사 결과 | 근거 |
|---|---|---|
| "PWA는 앱스토어 노출 불가" | **Android는 PWA→TWA 경로로 가능** — Bubblewrap/PWABuilder 둘 다 유지보수 중, Lighthouse 80점 요건은 폐지됨, 실제 승인 사례(2025-01) 확인 | 아카이브 §1.2 |
| "Flutter가 최적" | **React/TS 숙련자에게는 RN/Expo가 언어·상당수 로직(hooks, API 호출, ts-fsrs 등 순수 TS)을 보존** — Flutter는 언어(Dart)·UI·로직 전부 재작성 | 아카이브 §1.5 |
| "WebView 래퍼는 무조건 비권장" | 무조건은 아니다 — 네이티브 기능(푸시·오프라인·딥링크)을 실제로 얹으면 통과 사례 존재. 단, 리젝-재제출 반복은 각오해야 함 | 아카이브 §1.3, §1.4 |

**판단**: 웹 스택을 버릴 근거는 없지만, "네이티브 앱을 만든다면 Flutter"라는 ADR-001의 결론은 **재검토 대상**이다 — RN/Expo 쪽이 1인 React 개발자에게 구조적으로 유리하다는 근거가 이번에 나왔다. 다만 "React 숙련자가 Next.js 앱을 RN/Expo로 포팅하는 데 실제로 얼마나 걸리는지"의 실측 사례는 확보하지 못했다(미확인) — 공수 추정치 자체는 여전히 불확실하다.

## 4. 출시 경로 비교

| 레벨 | 경로 | 예상 공수(1인) | 비용 | 주요 리스크 |
|---|---|---|---|---|
| Lv0 | 개인 사용 유지(현행) | 0 | $0 | 없음 — 이미 완료 상태 |
| Lv1 | 웹 PWA 공개 배포 (Vercel) | 1~3주(인증·보안헤더·CI 정비) | $0~40/월(DAU에 따라, §5) | IDOR·보안헤더 부재 — 선행 작업 필수 |
| Lv2a | Android: PWA→TWA→Google Play | 수일(Bubblewrap/PWABuilder) + 테스터 12명×14일 대기 | $25 1회 | Webview spam 정책(자기 소유+실질 기능이면 해당 없음) |
| Lv2b | iOS: 홈 화면 추가(A2HS) 안내 강화, 스토어 없이 | 수일(UX 안내만) | $0 | 없음 — 심사 자체가 없는 경로 |
| Lv3 | iOS: Capacitor/PWABuilder로 App Store 도전 | 수주(정적 export 전환 + TTS/STT 네이티브 플러그인 교체) | $99/년 | **4.2(Minimum Functionality) 리젝 위험 높음** — 실사례 10회 연속 리젝도 있었음 |
| Lv4 | 네이티브 재작성(RN/Expo 권장, Flutter는 ADR-001 원안) | 수개월(추정, 실측 사례 없음) | $99+$25/년 | RN/Expo가 언어 유지로 상대적 유리, 단 공수 추정 자체가 불확실 |

**권고 순서**: Lv1 → Lv2a/Lv2b(동시 진행 가능, Android는 스토어·iOS는 A2HS) → Lv3/Lv4는 Lv1~2 운영 후 실사용자 수요가 확인되면 재검토. iOS App Store(Lv3)는 구조적으로 불리하므로 "스토어 등록"이 목적이 아니라 "iOS 사용자에게 닿는 것"이 목적이라면 Lv2b로 충분하다.

## 5. 영역별 조사 결과 요약

> 전체 수치·비교표·출처 URL은 [원자료 아카이브](../research/2026-07_release-feasibility-research.md) 참고. 아래는 결정에 필요한 핵심만 간추린 것이다.

### 5.1 서버·인프라·성능

- **10 DAU**: Vercel Hobby·Neon Free 전부 여유(2~20%만 사용).
- **100 DAU**: Neon Free의 compute 100 CU-hrs가 먼저 깨질 수 있음(접속이 하루 종일 퍼지면 scale-to-zero가 못 쉬어 60~180 CU-hrs 소요 가능) — Launch(종량제, ~$15/월)로 조기 전환 권장. **Neon Free 초과는 과금이 아니라 월말까지 DB 전면 정지**라는 점이 중요.
- **1,000 DAU**: 총 ~$40/월(Vercel Pro $20 + Neon Launch ~$20).
- **Vercel Hobby는 광고를 붙이는 순간 상업적 이용 금지 조항 위반** — 무광고 무료는 허용, 광고 도입 시 Pro($20/월) 필수.
- 이중 콜드스타트(Neon autosuspend + Vercel 콜드스타트)는 Fluid Compute(2025-04~ 기본)로 상당 부분 완화됨.
- 부하 검증: 1,000 DAU 피크가 ~10 RPS 수준이라 k6로 10~30 RPS 램프 테스트면 충분.
- 모니터링(Sentry Developer + UptimeRobot)은 전부 무료 티어로 구성 가능.

리뷰 API의 N+1(`api/review/route.ts:58`)과 next.config의 보안 헤더 부재(CSP·HSTS 등 0개)는 트래픽 규모와 무관하게 배포 전 손봐야 할 항목이다.

### 5.2 보안·개인정보·법규

- **현재(익명) 상태는 개인정보 관점에서 깨끗하다** — PII 컬럼 0개, deviceId(UUID)만 저장. 단 IDOR(임의 deviceId로 타인 데이터 접근 가능)는 실제 보안 결함이다.
- 스토어 등록에는 **수집이 0이어도 처리방침 URL이 필수**다(Google Data Safety·Apple Privacy Label 둘 다).
- 소셜 로그인(ADR-002) 도입 시에만 개인정보 동의 요건이 발생. 서버 STT(ADR-008) 도입 시에만 음성 데이터·국외 이전 고지가 필요 — **둘 다 출시 필수 조건이 아니라 기능 추가 시점의 조건**이다.
- HMAC 서명 토큰 같은 경량 보완이 계정 도입 전 단계에서 IDOR을 현실적으로 완화하는 방법이다.

### 5.3 수익성·시장 벤치마킹

- 한국 AdMob eCPM: 전면 $8.65·보상형 $12.00·**배너 $0.11(사실상 무의미)**. 1,000 DAU 추정 광고 수익은 월 ~$644(약 90만 원).
- 구독 벤치마크(RevenueCat 2026판, 11.5만 앱): 설치→유료 전환 Education 카테고리 중앙값 2.3%, **출시 12개월 후 앱의 중앙값 매출은 월 $72 미만**, 2년 내 $1K MRR 도달 앱은 17.3%뿐 — 이건 SenTalk 고유의 문제가 아니라 업계 전반의 기저율이다.
- 한국 경쟁 서비스(말해보카 매출 220억·구독 단일 모델, 스픽 ARR $100M·한국 매출 비중 90%, 듀오링고 한국 MAU 336만)는 전부 팀·투자 기반이다 — 1인 개발 성공 사례(김윤후: 8년 만에 월 1,000만 원)는 존재하나 예외적으로 오래 걸린다.
- "하루 1문장+FSRS+쉐도잉" 조합을 정면으로 파는 상용 경쟁자는 확인되지 않았다 — 포지셔닝 공백은 있으나, 공백이 곧 수요를 뜻하진 않는다.

## 6. 단계별 로드맵 + 체크리스트

각 단계는 **필수**(다음 단계로 넘어가려면 필요한 최소한)와 **고도화**(나중에, 필요해지면 — 지금 미뤄도 잃는 것 없음)로 나눴다. 지금 규모(개인+지인)에서 당장 체감되지 않는 최적화·자동화는 고도화로 미룬다 — "나중에 필요할 수도"는 지금 할 이유가 되지 않는다는 원칙을 그대로 적용했다.

### Step 0 — 결정 (착수 전 필수)

- [ ] 3축 재검토 결과 확정: 콘텐츠(§2.1)·학습 설계(§2.2)·기술 스택(§3) 각각 유지/보강/재시작 여부
- [ ] 전체 지속 여부: 개인 사용 유지(Lv0) vs 공개 추진(Lv1+)
- [ ] §7 결정 필요 사항 확인

### Step 1 — 도그푸딩 마무리 + 콘텐츠 위험 슬라이스 처리

**필수**
- [ ] `quote`·`movie` day_type 문장 4개년 전체 개수 집계 (하루 이내 작업)
- [ ] 위험 슬라이스 처리 방향 결정(재생성/교체/리스크 감수) — 실제 치환은 Step 2 이전 아무 때나
- [ ] 7일 이상 본인 실사용 + FSRS 간격 검증 (기존 NEXT-TASKS 계획과 동일)

**고도화**
- [ ] About 페이지 코퍼스 출처 표기(CHK-7) — 공개 배포 직전에만 필요, 지금은 안 급함

### Step 2 — 웹 PWA 공개 배포

**필수 (공개 배포 전에 반드시)**
- [ ] IDOR 완화: 최소 HMAC 서명 토큰(계정 도입 전 임시 조치, 반나절 작업)
- [ ] 보안 헤더(CSP·HSTS 등) `next.config.ts`에 추가 — 저비용·고효과
- [ ] 개인정보처리방침 URL 작성(데이터 수집 항목 정직하게 — deviceId+학습기록)
- [ ] Neon 커넥션을 pooler 방식으로, 함수 리전을 sin1/icn1로 (배포 시 설정 한 번)
- [ ] Vercel 배포 + 환경변수 설정

**고도화 (트래픽·문제가 실제로 생기면)**
- [ ] 분산 rate limit(Upstash 등) — 지금 규모에선 메모리 기반으로 충분
- [ ] review API N+1 수정 — DAU 100 미만에선 체감 안 됨
- [ ] CI/CD(GitHub Actions) — 수동 배포로 시작, 안정화 후 자동화해도 늦지 않음
- [ ] Sentry·UptimeRobot 연결 — 배포 후 문제가 보이면 그때
- [ ] Lighthouse 실측 — 배포 후 여유 있을 때

### Step 3 — Android 스토어(선택)

- [ ] Google Play 개인 개발자 계정 등록($25, 신분증+신용카드)
- [ ] Bubblewrap 또는 PWABuilder로 TWA 패키징, `/.well-known/assetlinks.json` 배치
- [ ] 테스터 12명 확보 → 14일 연속 비공개 테스트
- [ ] 스크린샷·아이콘·Data Safety 폼(Device ID+App activity로 정직하게 신고) 준비
- [ ] 프로덕션 신청

### Step 4 — iOS 대응 결정(선택)

- [ ] A2HS 안내 UX 강화(공유 시트→홈 화면에 추가, 스토어 없이) — 기본 권장
- [ ] 또는 Capacitor 전환(정적 export + 네이티브 TTS/STT 플러그인) 후 App Store 도전 — 리젝 반복 각오
- [ ] Apple Developer Program 등록 여부($99/년)는 Lv3 착수 시점에만 필요

### Step 5 — 수익화(선택, 지속 여부 결정 이후)

- [ ] 무료 유지 vs 광고(Vercel Pro 필수) vs 구독(Paddle/Lemon Squeezy — 법인 불필요, 5%+$0.50) 결정
- [ ] 광고 도입 시 About/처리방침에 광고ID·행태정보 조항 추가
- [ ] 구독 도입 시 가격 벤치마크(§5.3) 참고해 책정

### Step 6 — 확장(장기)

- [ ] 네이티브 앱 필요성이 실사용자 피드백으로 확인되면 ADR-001 재오픈 → RN/Expo 우선 검토
- [ ] P1(녹음)·P2(서버 STT, ADR-008 게이트) 계획대로 진행

## 8. 리스크 종합

- **저작권(콘텐츠)**: `quote`·`movie` 슬라이스 미검토가 가장 구체적인 리스크. 광고 수익 모델과 결합 시 악화됨.
- **보안(IDOR)**: deviceId 기반 인증은 임의 문자열로 타인 데이터 접근이 가능한 실제 결함 — 공개 배포 전 필수 완화 대상.
- **스토어 정책 변동성**: Apple 외부결제 수수료는 소송이 진행 중(2026-04 기준 미국 0%, 대법원 상고 병행)이라 유동적 — 결제 도입 시점에 재확인 필요.
- **유지보수 부담**: 인디 개발 사례(§5.2)에서 반복 확인된 패턴 — 성공한 앱도 방치하면 매출이 꺾인다(OKKY 사례: 1년 방치로 -20%). 공개 배포는 "만들고 끝"이 아니라 지속 운영 부담을 동반한다.
- **수익 기대치**: 업계 기저율(RevenueCat) 자체가 낮으므로, "서버비 회수" 이상을 목표로 잡을 경우 실망 가능성이 구조적으로 높다.
